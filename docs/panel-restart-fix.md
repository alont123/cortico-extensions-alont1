# 面板开关与重启状态修复

这次修复处理两类已确认的问题：详情配置里的“启用”开关与宿主激活状态不一致，导致重载或重启后关闭；人味内置模块展示了实际上没有独立启停效果的子开关。

## 原因与宿主契约

宿主用 `worlds.<id>.enabled` 决定进程启动时是否挂载扩展。宿主 World 卡片的激活/停用接口会同时保存该字段并挂载/卸载实例。普通配置保存只更新内存配置与 `config.json`，不会挂载或卸载扩展。

旧版共用面板把同一个根 `enabled` 字段也放进普通配置组。宿主表单保存一组配置时会提交该组全部字段；例如页面还保留 `enabled=false`，扩展已从另一处激活，随后修改间隔，旧表单就可能连同旧的 `false` 一起写回。此时实例仍在线，下一次按配置重载或启动时却关闭。

离线测试使用真实 `WorldAssembly`、SDK 配置校验与配置文件写入，确认了完整链路：

1. 打开旧版配置组，表单读到 `enabled=false`。
2. 通过宿主激活扩展，磁盘和运行态变为启用。
3. 保存业务设置时携带旧的 `enabled=false`，磁盘变为停用，但实例还在运行。
4. 新建装配读取磁盘配置后不再挂载；扩展调用 `WorldContext.restart()` 时也会按当前 `false` 停止。

`WorldAssembly.restart()` 本身不会清除 `enabled`；`WorldContext.restart()` 的约定是按当前 `cfg.enabled` 同步状态。本次问题可在扩展声明层解决，无需改变 Core 的启停语义。

## 修改范围

- 共用面板在原有声明和默认值补齐两个入口都排除根 `worlds.<id>.enabled`，宿主激活入口成为唯一启停入口。旧浏览器标签即使提交该字段，当前配置 schema 的校验也会忽略它。
- 保留有实际功能的嵌套业务开关，例如 CUA 自由活动、在玩什么的观察/余额、QQ 辅助视觉与候选调度。
- 人味只有一个宿主总开关，七个内置模块随总开关运行；移除无效的七个子开关声明，启动和重载不再合并、删除或重写宿主持有的启用字段。
- 在人味及七个对应独立扩展的教程和 README 标注不要同时启用。对应关系为 `affinity`、`learn`、`life`、`clock`、`together`、`mind`、`real`。两套同时运行会重复生成状态或提醒；提示不会自动停用任何已安装扩展，也不会迁移数据。

## 已遇到问题的用户如何恢复

1. 安装修复版本，并按宿主要求重载扩展或重启程序，然后刷新控制台页面，让页面使用新的配置声明。
2. 如果该扩展已关闭，在宿主 World 卡片上激活一次。人味与上述七个独立扩展请选择一套，不要同时启用。
3. 修改需要的业务设置，等配置保存成功后，再对标注需要重新挂载的设置使用宿主重新挂载。
4. 确认重载及后续重启仍保持已选的启用状态。需要关闭时，仍使用宿主卡片上的停用操作。

如果旧版已经把 `enabled=false` 写入配置，程序无法推断这是误覆盖还是用户主动停用。升级不会把所有扩展自动开启，也不会凭遗留的人味子开关覆盖明确保存的总开关。仍在运行但磁盘已是 `false` 的旧实例，应先按第一步重载宿主，再按第二步恢复；仅点击已经运行实例的激活按钮可能只返回“已在运行”。

如果激活时报错，应查看该次激活的具体错误。启动失败、外部服务未连接和人为停用，不应通过强制写 `enabled=true` 来掩盖。

## 验证与复现

安装本仓声明的依赖后运行：

```sh
node --import tsx --test tests/panels/host-persistence.test.ts
```

三项集成测试覆盖旧版故障链路、修复后业务保存与 World/进程重载保持启用、显式停用后仍保持关闭。已分别使用 Cortico SDK 0.2.1 和 0.2.7 执行，两个版本均为 3/3 通过。

另外检查了主仓 33 个 World 实际导出的配置声明，没有任何根启用字段残留；9 个现行业务子开关正常保留。`scripts/audit-panels.mjs --check` 会把根启用字段和人味遗留子开关重新出现视为错误。

这些验证使用合成配置与受控挂载适配器，没有启动真实 bot、连接 QQ/NapCat、向用户发送消息或修改生产部署。集成测试验证的是宿主配置和生命周期契约；外部服务的连接情况仍需在实际部署按对应扩展教程检查。
